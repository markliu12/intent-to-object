# Intent-to-Object

**把一个人还留有的微小自主运动，翻译成普通物件能执行的控制信号。**

本地优先的适配层。摄像头看着一个刻意的动作——头部微倾、持续眨眼——通过 MQTT 发出一个意图。灯不需要变智能，人不需要买眼动仪。

```
摄像头 → 面部关键点 → 姿态归一化 → 几何打分 → 驻留判定 → 风险策略 → MQTT
```

画面不出本机。没有账号，没有订阅，没有云。

## 当前状态：v0.2.1，端到端可跑，并且能测自己

| | |
|---|---|
| 感知 | MediaPipe Face Mesh（478 关键点），纯 CPU |
| 意图 | 几何基线：头部 roll 角 + 眼纵横比，均带驻留判定 |
| 输出 | MQTT，或仅终端 |
| 校准 | `ito calibrate` 用 20 秒动作拟合阈值，并把驻留时长下调到"你真的能保持"的程度；动作和休息态分不开时**拒绝写入** |
| 测量 | 延迟、每小时误触发、漏触发、重校时间，由工具产出，不靠手工估算 |
| 用户测试 | **零。本仓库目前不含任何真人数据** |

刻意不做的：多动作并存、训练分类器、手机 App、护理站后台，以及门锁、燃气、病床、护理呼叫——这些在加载配置时就会被拒绝，不是"以后再做"。

## 30 秒上手（无摄像头、无硬件）

```bash
pip install -e .
ito demo
```

这条命令跑的是**脚本生成的动作序列**，用来让你第一次运行就能看见一个命令走完整条链路，也让 CI 能抓住链路回归。它**不能**用来证明任何事在真人身上有效，报告里每次都这么写。

## 三个指标，三条命令

项目按三个数字验收，所以这三个数字都由工具产出，并且明确说出哪一段它测不了。

```bash
ito calibrate                 # 20 秒：拟合阈值、把驻留下调到可持续的时长、验证能触发
ito run --mqtt                # 实跑；摘要里是「帧→入队」（qos 0）或「帧→PUBACK」（qos 1）
ito review logs/audit.jsonl   # 逐条标记是否有意 + 统计漏触发 → 两个比率
```

`calibrate` 在动作和静息摇晃分不开时**不会**写阈值。这个拒绝就是重点：悄悄写进去一个坏阈值，比没有阈值更糟，因为直到凌晨三点误触才会有人发现。它还会在实测保持时长填不满默认驻留时把 dwell 调低——够得着却保持不住的阈值，是同一个故障换了身衣服。它同时把这次采集的会话存下来（`--session`，摄像头模式默认开启），以后改阈值时用 `ito replay` 复现，不必再让人做一遍动作。

`review` 需要一个人逐条回答，再加一个问题：有几次你做了动作但什么都没发生。两个比率都用会话记录里的曝光时长做分母，因为没有分母的次数不是测量；也因为只报误触发率，等于奖励一个"干脆更难触发"的阈值。规范的测法与仍然必须手工测量的部分（动作本身到成帧的间隔，那是相机的锅不是本项目的）见 [docs/metrics.md](docs/metrics.md)。

## 接摄像头

MediaPipe 目前没有 Python 3.13 的轮子，请用 3.10–3.12：

```bash
python3.12 -m venv .venv && . .venv/bin/activate
pip install -e ".[camera]"
ito doctor            # 缺什么会明确告诉你
ito run --show        # 干跑：只打印和记录，不发布
```

`ito run` 默认**不发送任何东西**，加 `--mqtt` 才会发布。第一次指向真实的灯之前，你应该先盯着它跑一段时间。

## 接真实物件

任何能订阅 MQTT 的东西都是合法输出。常见做法是用 Home Assistant 自动化订阅 `ito/intent/tilt_left`，或者让一台 ESP32 红外桥接固件（ir2mqtt、OMOTE、OpenMQTTGateway）订阅同一个 topic。本项目不写红外协议栈，具体见 [docs/hardware.md](docs/hardware.md)。

## 三个验收指标

1. **端到端延迟**：动作发生到 MQTT PUBACK。软件负责的那一段每次运行都会测；"动作→成帧"那一段是相机的。
2. **误触发率**：每小时、按活动类型分别统计，并与所要求的动作幅度一起报告。
3. **重校时间**：从"今天的动作不一样了"到**已验证可用**的新阈值，目标 ≤ 30 秒。

测法、分母和报告模板见 [docs/metrics.md](docs/metrics.md)。三项都还没有在真人身上测过——这是下一个里程碑，并且被明确写成"缺失"，不是"已经做到"。

## 几个刻意的设计决定

**一次只做一个动作。** 一个可靠的开关，胜过四个半可靠的手势。每多一个动作，用户就多付一次误触的信任成本。默认配置只有一个动作。

**先几何基线，再机器学习。** 头倾是一个角度，持续眨眼是一个比值。两个标量、一个死区、一个驻留计时器就够了，而且出错时你看着摄像头画面就能判断原因。少样本原型匹配留给"阈值分不开本人休息态和意图"的人——它会和这套基线在同样的录制数据上对比，而不是假设更好。

**触发之后必须释放。** 按住四秒只产生一条命令，不是十二条。对做不出快速动作的人，这是可用与不可用的分界。

**风险分级写在代码里，不是写在文档里。** 低风险直接发；中风险需要 `--confirm` 在场的人点头；高风险在配置加载时就拒绝启动，并说明这是设计如此。这样拒绝不可能被忽略，也不可能被一个笔误打开。

**校准失败比校准成功更重要。** `ito calibrate` 在动作无法与静息摇晃分离时拒绝写文件、返回退出码 3，并说明是"动作太小"还是"方向配错"。悄悄写一个坏阈值，是这个项目最不该犯的错。

**审计日志是功能，不是打日志。** 每条决策连同样本数值一起记录，并能渲染成一句人话：

```
14:02:11  tilt_left held 467 ms at confidence 0.81 -> sent to ito/intent/tilt_left (low risk, no confirmation needed)
```

验收标准是：护理人员不需要读代码，就能看懂一条记录。

**不是医疗器械**，不是生命安全设备，不能替代护理呼叫系统。它只服务于低风险便利——灯、风扇、电视——并且拒绝控制其他东西。指向任何要紧的东西之前，请先读 [docs/safety.md](docs/safety.md)。
